# Changelog

## 1.0.0-beta.85
- **A Reticulum 1.6.1 node's announce reads right.** Reticulum 1.6.1 (out 18 Nov) stamps every announce: it appends a marker, flags, a 14-byte proof-of-work stamp and the link cost to the announce's app data. Reference Reticulum hands applications the app data without it; urns didn't, so a 1.6.1 node's name read with 18 bytes of stamp after it (CI's NomadNet test: the Stump listed the node under its hash). urns now leaves the stamp out of what it keeps (the stamp isn't checked: 1.6.1 doesn't enforce stamps by default, and still takes a Stump's unstamped announces). 1.6.1's stamped path requests already read right.
- **A reply waits for a 1.6.1 app's path.** A 1.6.1 app answers a path request only once its announce stamp is made: 16 s on CI the first time, minutes on a phone. The Stump gave up on a reply after 15 s, and the reply was lost (CI's AutoInterface test: the app's message arrived, the Stump's answer never did). An LXMF message now waits up to 3 minutes for its recipient's path, asking again every 30 s after the first 15 s (the radio's airtime); other path waits are as they were.
- Tests: `announce_stamp` (new); the NomadNet and AutoInterface tests pass against Reticulum 1.6.1, their reference app using a cheap stamp so they never hang on making one.

## 1.0.0-beta.84
Two findings from the r36max team's review, and a third found while fixing them.
- **Removing a pack deletes only the pack's own places.** With "delete what it keeps too", the Provisioner and Arborist took the folders to delete from the pack's record (`.from_pack`), read from the board or the Stump's folder, and trusted it. A tampered record could empty a board's SD card, and on a computer Stump an entry such as `/` or `..` reached outside its folder: anything the user running the Provisioner owns. Now only `plugins/<its plugin>`, its own Tools section (never one the Stump ships) and `home/<one file>` are taken from it, home files are deleted one by one, and a folder such as `lib/` given an `install.py` is never taken for a plugin.
- **A pack's name must be a plain name** (as Arborist already asked). A downloaded pack named `../..` wrote its tools outside a computer Stump's folder, and removing it deleted there. A pack zip is also unpacked under a plain name.
- **An identity that won't read whole is never taken as "no identity".** On a CAM, a garbled read let a restore write the new identity over the old one without saving it. The board now sends each identity file's size and SHA-256 and the copy is checked against them (tried twice); a computer Stump's damaged file counts too. A restore then stops and changes nothing, and nothing is made over it. When only the mailbox key differs, the one there is saved first too. Same in Arborist.
- Tests: the crafted record (kept relative, so it can never reach outside the test's own folder), garbled reads, a mailbox-only difference, a damaged file, unsafe pack names.

## 1.0.0-beta.82
The test repo (potential-broccoli) merged in: packed text, the November code review's fixes, and two tester packs. It had numbered this work "beta.74", then "beta.78"; it ships here as beta.82, with everything of beta.74 to beta.81.
- **Packed text: more of a chat line in each LoRa packet.** A packet holds 295 bytes of LXMF content whatever is in it; what a Stump sends is text, in three languages, much of it its own replies. Between two ends that both say they read it (a fifth item in their LXMF announce, `{"z": 1}`), a message's content now goes packed (`urns/ztext.py`): about 60% of its bytes for ordinary chat, a sixth for `/help` (800 bytes, a link and a transfer, now 134 bytes, one packet). To anyone else (Sideband, MeshChat, an older FireFly or Stump) text goes as it always did.
  - The format is a standard one cut to size: a DEFLATE block whose Huffman tables and dictionary are fixed and never sent. Reading it is the platform's own inflate (MicroPython's `deflate`, zlib on a computer), at most 2048 bytes out: no parser of ours meets what the radio brings. Writing is 80 lines of Python, the same file on a board, a computer and in FireFly.
  - `#lora-mesh` between Stumps over the radio: a piece is sized as sent, so more lines go in the same bytes on the air (a long names list often whole); the broadcast for several Stumps goes as `lb2`, packed, when all of them read it.
  - `LXMF_PACKED_TEXT = False` in config.py turns it off. Docs: CLIENT_QUICKSTART, *Packed text*.
- Tests: `ztext` (the format's tables and fixed messages; never longer; random and cut-short contents; the announce flag; who gets packed text; switched off; radio pieces; `lb2`); `tests/reference` (the announce still reads in upstream LXMF; packed messages both ways with reference LXMF and plain zlib; a batch too long for one packet fits packed).
- **Meter pack** (`packs/meter-pack`): a tester's counter of what the Stump sends people's apps. `/meter` gives the bytes of text, the bytes as sent and how many messages fit one LoRa packet; `/meter 3` sends a fixed 403-byte test text (over a link as it is, one packet packed). `/meter room` estimates from the room's own latest lines, from the Wi-Fi page too (which is told that only LXMF messages are counted). It runs on any firmware since beta.53, so a kit is measured on beta.77, updated, and measured again. Since 1.2 it also counts what goes to other Stumps (a room's lines over the chain or the radio, the radio broadcast), which is all there is to count when everyone is on a Wi-Fi page. Since 1.3 the radio is counted apart from the chain, and so are the lines people's apps send in. It only counts: nothing sent is changed, nothing stored. Test: `meter_pack` (passes on beta.73, beta.77, beta.81 and this release).
- **Marco Polo pack** (`packs/marcopolo-pack`): a tester's call and answer between Stumps. `/marco start 10 3 30` on one Stump writes ten calls in `#lora-mesh`, 30 s apart; every other Stump with the pack answers polo; `/marco` gives, for each, the polos back, the calls lost and the round trip (min / average / max). The lines travel as a person's do, which is the path being timed; a long call answered only once its last piece is in. Nothing on the air until a run is started. Test: `marcopolo_pack` (passes on beta.73, beta.77, beta.81 and this release).
- **Code review, Nov 2026**, the fixes that came with it:
  - **A message carrying an LXMF stamp was dropped by a board as forged.** A stamp is a fifth item after the four that are hashed and signed; to get the message's id the router packed those four again. A board's floats are 32 bits: the timestamp read and written back wasn't the sender's eight bytes, the id came out different, the signature failed ("its signature doesn't match its sender"). Never on a computer Stump, nor in the tests against upstream LXMF (both have 64-bit floats). The id is now made from the bytes received.
  - **The LXMF router remembered without limit**: the id of every message taken in (30 days each, and a pass over all of them at each message), and a name for every address that ever announced, of any kind. Messages from addresses not heard yet cost their sender nothing to make, so a radio (or a device on the Wi-Fi) could fill a board's memory. Both are bounded now (256 ids and 160 names on a board, 4096 and 768 on a computer), the oldest going first; expired ids are cleared once a minute.
  - A packet, a link packet and a resource are taken in by one function (three copies had drifted: only one marked how the message was encrypted, only one proved a repeated packet). The announce's data is made in one place: a stamp cost asked for at registration was in the first announce only.
  - The Provisioner's manifest leaves out hidden files and folders (a linter's cache left in `final_firmware/` was taken for firmware).
  - urns: imports nothing used (49, mostly `gc` beside `_gc_collect()`), in 19 files. No change in behaviour.
  - Tests: `lxmf_router` (a stamped message with a real 64-bit timestamp; the three ways in; repeated packets; the caps); `provisioner` (hidden files). `lxmf_router` fails on beta.73: the stamped message refused, 204 ids held where 50 are allowed.
  - Noted for later, not changed: docs/TODO.md (*From the review of November 2026*).

- **The chat bridge says which of its steps held the Stump** (a message out, to whom; the chain's Stumps; the radio's turn; a memory clean-up), and the time a memory clean-up and a chain-secret signature take are said when slow (`[mem] ...`, `[chain secret] ...`, at most once a minute). A WROVER was "busy for 3203 ms: the chat bridge (mesh sends)", by which part not said.
- **A board Stump joins its chain over the home Wi-Fi**, like a computer Stump. A CAM or a WROVER that's a chain member used its one Wi-Fi connection for the hotspot of the Stump before it, so it had no home address and couldn't be opened from the home network. With `CHAIN_PARENT_IP` (the first Stump's address on the home Wi-Fi) it stays on `WIFI_SSID` (home address, clock, internet) and links to the first Stump there; its own hotspot still serves visitors, its Heltec and Stumps below it. When the router moves the first Stump, it finds it again on that network (discovery broadcast, then `/chain.json`: root, same chain, taking links there), never leaving it to scan hotspots. The Provisioner offers it in the chain question ("Over the Wi-Fi it joins"), finds the first Stump from the computer, and asks for the chain secret (needed). `/chain.json` `uplink.over_lan`. docs/CHAIN.md.
- **A board set up for the router stays on the router.** Off it (not there at boot, or dropped), it joins it again every 30 s and nothing else: it used to give up on the router after a minute and hunt for Stump hotspots, and joined the first Stump's (a WROVER with the router settings came up on "LaBuche-Stump.web.app" with no home address). The chip's own reconnects are on before the first join.
- **A board in a chain, and its Heltec, on the router by default** (the Provisioner): "Over the router (recommended): like your other Stumps" is the chain question's first choice (the router's Wi-Fi asked there if it wasn't), and the Heltec's first choice is the router too, at a fixed address past the router's DHCP range (.222 on this computer's network). The hotspot ways stay, as second choices.
- **The setup's last check reaches the board the way people will.** After the USB checks ("USB CHECKS PASSED", no longer "certified" on their own), the Provisioner opens the board's page from this computer at its router address and checks its Heltec is connected (`/hw.json`), waiting for it to come up. Certified only if both: a board on another Stump's hotspot, a computer on another network, no answer, another Stump at that address or a Heltec not connected each fail, saying which. The summary's "Open it at" is that address. (A WROVER was "certified" with an address that worked from nowhere the computer was.)
- **Room to work in** (`urns/mem.headroom`). MicroPython's ESP32 port grows its heap only when an allocation fails *after* a full collection, so the heap stays just big enough for what's live and every few hundred KB of churn (a page or two) costs a full collection, ~2 s on a WROVER, however few the code asks for. At boot the Stump allocates and frees 2 MB once, so the port adds that much heap and the churn has room before the next collection. The boot log says the heap's size (`[mem] at boot: ...`, `[mem] with room to work in: ...`).
- **Memory clean-ups only when memory is low** (`urns/mem.py`). The code forced a full garbage collection at 65 places, several per packet (a chain secret's signature and check, proofs, announces) and after every DNS answer of the captive portal: from boards without PSRAM. On a WROVER one takes ~2 s ("a memory clean-up took 2040 ms (839 KB in use)"), so each packet and each phone's portal check froze the Stump for seconds. Now a collection runs only under 25% (or 96 KB) free; MicroPython still collects by itself when the heap is full. The /admin plugin RAM figure no longer forces one.
- **The watchdog names what held the Stump.** "the Stump was busy for N ms" now ends with what it had started last (a web page and its address, a packet and the interface it came on, a plugin's callback or timer, connecting to the Heltec, an LXMF send, the chat bridge, the chain watch, a propagation stamp check), and says each long one (at most one line per 10 s), not only a new record. Found on a WROVER busy 15 s, by what not said.
- `--diag`: a chained Stump's hotspot address is 192.168.<its number>.1 (it always said 192.168.4.1).
- Tests: provisioner_test (no saved settings; the last check: hotspot, other network, page and Heltec, Heltec down, another Stump, no answer), `mem_low` (no clean-up with plenty free, one when low), `chain_lan` (a board member over the home Wi-Fi: settings, interfaces, found again when moved), `heltec_connect` (there, refused, nobody answering: no step holds the Stump), `keepalive_boot` (the busy line names what), `wrover_board` (SD pins per chip, the voice engines from the card, the board's name), `provisioner_test` (chip detection, the board step on a bridge port per chip, the image and offset per chip, the voice engines to the card on a WROVER, in flash on a CAM).
